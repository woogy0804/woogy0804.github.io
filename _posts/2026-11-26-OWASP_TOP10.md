웹사이트에 로그인하면 자신의 정보를 조회하거나 수정할 수 있다. 그런데 주소에 있는 회원 번호를 바꾸는 것만으로 다른 사람의 정보까지 볼 수 있다면 어떨까? 로그인 기능이 정상적으로 작동하더라도, 접근 권한을 제대로 확인하지 않으면 이런 문제가 발생할 수 있다.



웹 보안에 관심을 가지고 공부하면서, 어떤 문제들이 주요 보안 위험으로 다뤄지는지 알아보기 위해 **OWASP Top 10**을 살펴봤다. 이번 글에서는 2025년판의 주요 변화를 간단히 정리하고, 그중 **접근 제어 실패(Broken Access Control)**의 개념과 발생 원리, 대응 방법을 알아보려고 한다.



## 1. OWASP Top 10과 2025년의 변화



OWASP Top 10은 웹에서 주의해야 할 주요 보안 위험을 열 가지 범주로 정리한 자료다. 웹 보안에서 어떤 문제를 다루는지 전체적으로 살펴보는 데 참고할 수 있다. 각 항목에는 관련된 여러 취약점이 포함된다.



2025년판의 목록을 살펴보면서 이전 버전인 2021년판에서 어떻게 변화되었는지 알아보자.



| 구분 | 항목 | 2021년판과 비교 |

| --- | --- | --- |

| A01 | Broken Access Control | 1위 유지, SSRF 통합 |

| A02 | Security Misconfiguration | 5위 → 2위 |

| A03 | Software Supply Chain Failures | 기존 컴포넌트 관련 항목의 범위 확장 |

| A04 | Cryptographic Failures | 2위 → 4위 |

| A05 | Injection | 3위 → 5위 |

| A06 | Insecure Design | 4위 → 6위 |

| A07 | Authentication Failures | 7위 유지, 명칭 변경 |

| A08 | Software or Data Integrity Failures | 8위 유지, 명칭 일부 변경 |

| A09 | Security Logging and Alerting Failures | 9위 유지, 명칭 변경 |

| A10 | Mishandling of Exceptional Conditions | 새 범주로 추가 |



주요 변화로는 보안 설정 오류(Security Misconfiguration)의 순위 상승과 공급망 항목의 범위 확장(Software Supply Chain Failures)이 있다. 공급망 항목은 사용하는 라이브러리의 취약점뿐 아니라 소프트웨어를 만들고 배포하는 과정까지 다룬다. 오류나 예외 상황을 부적절하게 처리하는 문제(Mishandling of Exceptional Conditions)도 새 범주로 추가됐다.



접근 제어 실패(Broken Access Control)는 2021년에 이어 1위를 유지했다. 이전에 별도 항목이었던 SSRF도 이 범주에 포함됐다.



다만 이 순위는 실제 공격 건수만으로 정해진 것은 아니고 보안 테스트 데이터와 커뮤니티 설문 등을 반영한 결과이므로, 주요 위험을 이해하기 위한 기준으로 받아들이면 좋을 것 같다.



## 2. 접근 제어 실패의 개념



접근 제어는 **사용자가 어떤 데이터와 기능을 사용할 수 있는지 제한하는 것**이다. 쇼핑몰 회원은 자신의 주문을 조회할 수 있지만, 다른 회원의 주문을 마음대로 보거나 상품 가격을 변경할 수는 없다.



여기서 인증과 인가를 구분할 필요가 있다. **인증(Authentication)**은 사용자가 누구인지 확인하는 과정이고, **인가(Authorization)**는 그 사용자에게 특정 행동을 허용할지 판단하는 과정이다. 로그인은 인증에 해당하며, 로그인한 회원에게 특정 주문을 보여줘도 되는지 판단하는 것은 인가에 해당한다.



즉, 서버가 로그인한 사용자를 확인했더라도 권한 검사가 끝난 것은 아니다. 그 사용자가 요청한 정보와 기능을 사용할 수 있는지도 확인해야 한다.



**접근 제어 실패는 이 권한 검사 과정이 없거나 잘못 적용되어 사용자가 허용된 범위를 벗어나는 문제다.** 다른 사람의 정보를 조회하는 것뿐 아니라 데이터 수정·삭제, 관리자 기능 실행 등으로 이어질 수 있다.



접근 제어가 중요한 이유가 여기에 있다. 주문 조회 기능에서 검사가 빠지면 개인정보가 노출될 수 있고, 수정이나 삭제 기능에서 빠지면 다른 사람의 데이터를 바꾸거나 없앨 수도 있다. 조작 방법은 단순하지만 영향을 받는 데이터와 기능에 따라 피해는 커질 수 있다.



## 3. 접근 제어 실패의 주요 사례



### IDOR과 수평적 권한 상승



주문 내역을 조회하는 주소가 다음과 같다고 가정해 보자.



```text

https://example.com/mypage?user_id=1004

```



로그인한 사용자는 1004번 회원이다. 이 상태에서 `user_id`를 `1005`로 바꿨을 때 다른 회원의 비공개 주문 내역이 보인다면 접근 제어에 문제가 있는 것이다.



이런 상황은 서버가 로그인 여부만 확인하고, URL에 들어 있는 회원 번호로 데이터를 찾아 반환할 때 발생할 수 있다. 요청자는 1004번 회원인데 조회 대상은 1005번 회원이라는 점을 검사하지 않은 것이다.



이처럼 식별자를 조작해 권한 없는 데이터에 접근할 수 있는 취약점을 **IDOR(Insecure Direct Object Reference)**이라고 한다. 식별자는 회원 번호뿐 아니라 주문 번호, 문서 ID, 파일명일 수도 있다.



문제의 원인은 URL에 번호가 있다는 사실이 아니라, 해당 데이터에 대한 접근 권한을 확인하지 않는 데 있다. 같은 수준의 사용자 사이에서 접근 범위를 벗어나는 경우는 **수평적 권한 상승**의 예다.



### 관리자 기능과 수직적 권한 상승



일반 사용자 화면에 관리자 메뉴가 표시되지 않더라도 서버의 관리자 기능이 보호되는 것은 아니다. 사용자는 화면의 버튼을 누르는 대신 해당 기능의 주소로 직접 요청을 보낼 수 있기 때문이다.



예를 들어 회원 삭제 기능이 관리자 메뉴에만 연결되어 있어도, 서버에서 권한을 검사하지 않으면 일반 사용자가 직접 요청해 실행할 수 있다. 이렇게 자신의 역할보다 높은 권한의 기능을 사용하는 것은 **수직적 권한 상승**에 해당한다.



관리자 주소를 복잡하게 숨겨 놓는 방법만으로는 충분하지 않다. 주소가 알려졌을 때 그 요청을 허용할지는 서버의 권한 검사에서 결정되어야 한다.



### SSRF를 통한 내부 자원 접근



SSRF는 이전에 PortSwigger Academy에서 간단히 공부하고 실습해 본 주제다. 이번에 2025년판을 살펴보면 접근 제어 실패에 통합됐다는 점을 확인할 수가 있다.



**SSRF(Server-Side Request Forgery)**는 서버가 의도하지 않은 대상으로 요청을 보내도록 만드는 취약점이다. 예를 들어 서버가 사용자가 입력한 URL의 정보를 가져오는 기능에서 요청 대상을 적절히 제한하지 않으면 문제가 생길 수 있다.



이때 요청을 보내는 주체는 사용자의 브라우저가 아니라 서버다. 따라서 사용자가 직접 접근할 수 없는 내부 서비스에도 서버를 통해 접근할 가능성이 생긴다. PortSwigger에서는 서버 자신이나 다른 내부 시스템을 대상으로 하는 사례를 제시하고 있다.



앞의 IDOR과 공격 과정에서 차이가 있지만, 서버를 통해 허용되지 않은 자원에 접근할 수 있다는 점은 공통적으로 살펴볼 수 있었다.



## 4. 대응 및 방어 방법



앞의 사례들은 접근 대상이 데이터인지, 관리자 기능인지에 따라 모습이 다르다. 하지만 요청을 처리하기 전에 필요한 권한을 확인해야 한다는 점은 같다.



먼저 사용자별로 어떤 데이터와 기능을 사용할 수 있는지 정해야 한다. 이를 바탕으로 서버가 요청마다 권한을 검사한다. 화면에서 버튼을 숨겼거나 이전 단계에서 검사했다는 이유로 실제 처리 요청의 검사를 생략해서는 안 된다.



기본 원칙은 **Deny by Default**와 **최소 권한**이다. 공개 자원을 제외하고 허용 조건을 만족한 요청만 처리하며, 사용자에게 필요한 범위의 권한만 부여하는 것이다. 공통 검사 로직을 사용하면 기능별 누락을 줄이는 데 도움이 되지만, 로그인 여부와 개별 데이터의 접근 권한은 구분해서 확인해야 한다.



또한 식별자를 UUID처럼 추측하기 어려운 값으로 바꾸더라도 권한 검사는 필요하다. 유효한 식별자를 알게 된 사용자에게 데이터를 보여줘도 되는지는 별도로 판단해야 하기 때문이다.



구현 후에는 정상적인 요청과 함께 거부해야 하는 요청도 제대로 확인해야 한다. 회원 A가 자신의 주문을 조회할 수 있는지뿐 아니라, 다른 회원의 비공개 주문에는 접근할 수 없는지도 확인하는 식이다.



## 5. 정리



이번에 정리하면서 꼭 기억해야 할 부분은 로그인 확인과 권한 확인은 다르다는 점이다. 사용자가 누구인지 확인했더라도, 그 사용자가 요청한 데이터와 기능을 사용할 수 있는지는 따로 판단해야만 한다.



웹 분야는 아니지만 현재 AWS IAM을 공부하고 권한 오용을 탐지하는 프로젝트를 진행하고 있는데, 사용자에게 어디까지 작업을 허용할지에 대해 살펴보고 있다. 구현 방식은 다르지만, 공통적으로 권한의 범위를 정하고 적용하는 과정이 중요하다는 점을 알 수 있었다.



오늘 정리한 내용을 바탕으로, 웹 해킹 문제를 풀거나 개발을 할 때는 요청이 어떻게 처리되는지와 함께, 그 과정에서 어떤 권한을 확인하는지도 살펴보려고 한다.
