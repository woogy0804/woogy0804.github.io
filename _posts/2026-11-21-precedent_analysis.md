## 1. 판례 소개와 선정 이유

- 사건명: 과징금부과처분취소
- 사건번호: 대법원 2018두56404 (원심: 서울고등법원 2016누64533)
- 선고일: 2021. 8. 19.
- 당사자: 원고(주식회사 케이티) · 피고(개인정보보호위원회, 경정 전 방송통신위원회)
- 자료: [판결문 원문(국가법령정보센터)](https://www.law.go.kr/판례/(2018두56404)) · [대법원 보도자료](https://people.scourt.go.kr/portal/news/NewsViewAction.work?seqnum=7918&gubun=4)

해킹 사고가 발생해 수천만 건의 개인정보가 빠져나갔다면, 해당 기업은 당연히 과징금을 물어야 할 것 같다. 그런데 법원이 기업의 손을 들어준 사례가 있다.

대법원 2018두56404 판결은 KT 홈페이지 해킹 사고에 부과된 과징금 처분을 취소한 사건이다. 보안 취약점이 실제로 존재했고 대규모 유출까지 일어났음에도, 법원이 '기술적 보호조치 의무를 위반하지 않았다'고 판단한 기준이 무엇인지 궁금해 이 판례를 선택했다. 이 글에서는 사건이 일어난 기술적 배경과 양측의 주장, 상급심과 대법원의 판단 차이를 정리하고, 현행법 기준으로 다시 살펴본 내용을 덧붙였다.

## 2. 배경: 사건의 경과와 유출된 개인정보

### 2.1 정상적인 요금 조회 과정

이해하기 쉽도록 이용자가 홈페이지에서 요금을 조회하는 정상 흐름부터 살펴보자.

1. 이용자가 홈페이지에 로그인한다.
2. 웹 서버는 통합인증 서버를 통해 본인 여부를 확인하고, 인증 정보를 이용자 PC에 전달한다.
3. 회원으로 로그인하면 9자리 숫자로 된 고유한 '서비스계약번호'가 브라우저의 쿠키에 저장된다. 쿠키는 로그인 상태나 식별 값을 브라우저에 임시로 담아두는 작은 데이터 조각이다.
4. 이용자가 '요금명세서 보기'를 누르면 웹 브라우저는 이 서비스계약번호를 담아 웹 서버로 요청 메시지를 보낸다.
5. 웹 서버는 데이터베이스(DB) 서버에서 해당 번호의 요금 정보를 찾아 이용자 PC로 보내고, 브라우저 화면에 띄운다.

### 2.2 해커의 공격 방법: 파라미터 변조와 IDOR

이 사건에는 웹 보안에서 자주 언급되는 **파라미터 변조(Parameter Tampering)** 공격이 쓰였다. 파라미터는 브라우저가 서버에 요청을 보낼 때 함께 전달하는 입력값이다. 이 사건에서는 '서비스계약번호'가 그 역할을 했다.

조금 더 구체적으로는 **IDOR(Insecure Direct Object Reference, 부적절한 직접 객체 참조)** 취약점에 해당한다. 서버가 "로그인한 사람이 맞는지(인증)"만 확인하고, "그 사람이 요청한 데이터가 정말 본인 것이 맞는지(인가)"는 확인하지 않을 때 발생한다.

해커는 다음 순서로 데이터를 빼냈다.

1. 자신의 PC에 **파로스(Paros)**라는 웹 프록시 프로그램을 설치했다. 프록시 프로그램은 브라우저와 서버 사이에서 오가는 통신 데이터(패킷)를 중간에 가로채 내용을 보거나 수정할 수 있는 도구다.
2. 본인 계정으로 정상 로그인한 뒤 '요금명세서 보기'를 눌렀다.
3. 요청 메시지가 웹 서버로 넘어가기 직전, 파로스 프로그램을 이용해 전송을 멈췄다.
4. 요청 메시지 안에 들어 있던 해커 본인의 서비스계약번호를 **임의의 9자리 숫자**로 바꿔 적은 뒤 전송 버튼을 눌렀다.
5. KT 웹 서버는 전달받은 번호가 현재 로그인한 해커의 번호인지 대조하지 않았다. 대신 DB 서버에서 그 임의의 번호에 해당하는 다른 고객의 요금명세서 정보를 그대로 꺼내 응답 메시지로 돌려보냈다.

### 2.3 유출 규모와 문제가 된 개인정보

해커는 2013년 8월 8일부터 2014년 2월 25일까지 이 과정을 반복해 총 **11,708,875건**의 개인정보를 수집했다.

유출된 항목은 요금정보, **고객의 이름, 주민등록번호, 주소, 서비스가입정보** 등이다.

여기서 눈여겨볼 지점이 있다. 이름, 주민등록번호, 주소 같은 민감한 정보는 실제 웹 브라우저 화면에는 표시되지 않는 값이었다. 하지만 웹 서버가 화면에 보여줄 필요도 없는 데이터까지 응답 패킷에 통째로 실어 보냈고, 해커가 파로스 프로그램으로 패킷 원문을 확인하면서 이 정보까지 모두 빠져나갔다.

## 3. 양측 주장과 법원의 판단

### 3.1 판단에 쓰인 법 조항

사고 당시 통신사 같은 정보통신서비스 제공자는 개인정보보호법이 아니라 구 정보통신망법의 적용을 받았다. 핵심 조항은 세 가지다.

- **구 정보통신망법 제28조 제1항 제2호**: 개인정보의 분실·도난·누출·변조·훼손을 막기 위해 불법적인 접근을 차단하는 침입차단시스템 등 접근통제장치를 설치·운영해야 한다.
- **구 정보통신망법 시행령 제15조 제2항·제6항**: 개인정보를 처리할 수 있도록 체계적으로 구성한 데이터베이스시스템을 '개인정보처리시스템'으로 정의하고, 구체적인 보호조치 기준을 고시에 위임한다.
- **구 「개인정보의 기술적·관리적 보호조치 기준」(방송통신위원회 고시) 제4조 제9항**: 취급 중인 개인정보가 인터넷 홈페이지, P2P, 공유설정 등을 통해 열람 권한이 없는 자에게 공개되거나 외부로 유출되지 않도록 개인정보처리시스템 및 개인정보취급자의 컴퓨터에 조치를 취해야 한다.

### 3.2 양측의 주장

| 구분 | 핵심 주장 |
| :--- | :--- |
| 피고 (개인정보보호위원회) | 파라미터 변조라는 잘 알려진 취약점을 방치해 대규모 유출이 발생했다. 고시 제4조 제9항의 보호조치 의무를 위반했으므로 과징금 부과는 정당하다. |
| 원고 (KT) | 개발 단계부터 보안 점검 도구를 연동했고, 정기적인 모의해킹과 침입방지시스템(IPS) 운영 등 당시 기술 수준에서 기대할 수 있는 보호조치를 다했다. |

### 3.3 대법원의 판단

대법원은 두 가지 쟁점으로 나누어 판단했다. 법리적인 전제는 피고(개인정보보호위원회)의 주장을 받아들였지만, 최종 결론은 원고(KT)의 손을 들어주며 상고를 기각했다.

#### 첫째, 웹 서버도 '개인정보처리시스템'에 포함된다

대법원은 고시 제4조 제9항이 내부 직원의 실수뿐 아니라 외부 해킹으로 인한 유출 방지도 직접 규율한다고 보았다. 또한 DB 서버와 연결되어 개인정보를 주고받는 웹 서버 역시 개인정보처리시스템의 일부라고 명확히 밝혔다.

> "이 사건 고시 제4조 제9항의 '개인정보처리시스템'은 개인정보의 생성, 기록, 저장, 검색, 이용과정 등 데이터베이스시스템(DBS) 전체를 의미하는 것으로, 데이터베이스(DB)와 연동되어 개인정보의 처리 과정에 관여하는 웹 서버 등을 포함한다고 봄이 타당하다."

#### 둘째, KT가 기술적 보호조치 의무를 위반했다고 보기는 어렵다

대법원은 기업이 취해야 할 보호조치의 기준을 '모든 해킹을 100% 막아내는 것'이 아니라 **'사회통념상 합리적으로 기대 가능한 정도의 기술적 보호조치'**라고 해석했다.

> "정보통신서비스 제공자 등이 취급 중인 개인정보가 인터넷 홈페이지 등에 대한 해킹 등 침해사고에 의해 유출되지 않도록 개인정보처리시스템과 개인정보취급자의 컴퓨터에 취하여야 할 사회통념상 합리적으로 기대 가능한 정도의 기술적 보호조치라고 해석할 수 있다."

대법원이 KT의 의무 위반을 인정하지 않은 근거는 다음과 같다.

1. **방대한 소프트웨어의 한계**: 대규모 홈페이지처럼 소스코드가 방대하고 입력 파라미터의 경우의 수가 많은 시스템에서는, 개발 단계에서 모든 파라미터 변조 상황을 미리 예상해 막아내기 쉽지 않다.
2. **당시의 개발 관행**: 정상 로그인을 마친 이용자라면 조회 권한도 함께 보장된다고 보고 프로그램을 설계하는 것이 당시로서는 통상적인 방식이었다.
3. **결과책임 경계**: 사고가 난 뒤 KT가 파라미터의 계약번호와 로그인 이용자 정보를 대조하도록 소스코드를 수정해 취약점을 없앤 것은 사실이다. 하지만 사후 조치가 비교적 쉬웠다는 이유만으로 법 위반을 단정하면 기업에 무리한 결과책임을 묻게 된다.

> "사후 시정조치가 비교적 손쉽게 이루어졌다는 사정에만 주목하여 이 사건 고시 제4조 제9항 위반 여부를 판단한다면 이는 결과책임을 묻는 것으로 귀결될 우려가 크다."

4. **사전 보안 점검 이력**: KT는 2006년부터 국제웹보안표준기구(OWASP)의 10대 보안 취약점을 찾아내는 자동화 점검 도구를 자체 보안점검관리 포털에 연동해 개발·유지보수 단계에 적용했다. 또한 2012년 11월과 2013년 7월에 모의해킹을 수행했고, 국가정보원 인증 침입방지시스템(IPS)을 설치·운영하는 등 취약점을 줄이기 위한 조치를 꾸준히 이어왔다.

## 4. 상급심 비교와 현행법 기준 검토

### 4.1 원심(서울고법)과 대법원의 비교

이 사건은 최종 결론(KT 승소)은 같지만, 대법원이 2심(원심)의 법리 해석을 정면으로 바로잡았다는 점에 의미가 있다.

| 비교 항목 | 원심 (서울고등법원 2016누64533) | 대법원 (2018두56404) |
| :--- | :--- | :--- |
| 고시 제4조 제9항 적용 범위 | 기업 내부 요인에 의한 유출 방지용이며, 파라미터 변조 같은 외부 해킹은 직접 규율하지 않는다. | 내부 부주의뿐 아니라 외부 해킹에 의한 유출 방지도 직접 규율한다. |
| 웹 서버의 시스템 포함 여부 | 내부 영역의 데이터베이스관리시스템(DBMS)만 해당하고, 웹 서버나 웹 페이지는 포함되지 않는다. | DB와 연동되어 개인정보 처리에 관여하는 웹 서버 등 데이터베이스시스템(DBS) 전체가 포함된다. |
| 보호조치 의무 위반 여부 | 위반하지 않았다. (원고 승소) | 위반하지 않았다. (상고 기각) |

원심은 웹 서버를 개인정보처리시스템에서 제외해 KT의 책임을 부정했다. 대법원은 그 해석이 부적절하다고 지적하면서 웹 서버를 포함시켰지만, KT가 평소 기울인 보안 노력을 인정해 최종 결론은 유지했다.

### 4.2 사건 이후 법 개정과 현재 기준 결론 예측

이 사건은 2013~2014년 사고에 대해 구 정보통신망법을 적용한 판결이다. 이후 관련 법령은 크게 두 차례 바뀌었다.

1. **법령 통합(2020년 데이터 3법 개정)**: 구 정보통신망법의 개인정보 보호 규정이 **「개인정보 보호법」**으로 통합되었다. 기존 고시 제4조 제9항의 내용은 현재 개인정보보호법 제29조(안전조치의무), 시행령 제30조, 그리고 「개인정보의 안전성 확보조치 기준」 제6조 제3항으로 이어졌다.
2. **과징금 기준 강화(2023년 전면 개정)**: 개인정보 유출 시 과징금 상한이 '위반행위 관련 매출액의 3%'에서 **'전체 매출액의 3%(위반행위와 관련 없는 매출액 제외)'**로 높아졌다.

그렇다면 **현재 기준으로 똑같은 사고가 발생해도 같은 결론이 나올까?**

법리적인 기준 자체는 그대로다. 지금도 기업에 무조건적인 결과책임을 묻지 않고, 사고 당시 보편적으로 알려진 보안 기술 수준을 기준으로 합리적인 조치를 다했는지 따진다.

하지만 **실제 결론은 달라질 가능성이 높다.** 대법원이 판단 기준으로 삼은 '보편적 보안 기술 수준'이 2013년과 지금은 크게 다르기 때문이다. 오늘날에는 파라미터 변조(IDOR)를 막기 위해 서버에서 세션 주인과 요청 객체의 소유권을 대조하는 것이 웹 개발의 가장 기초적인 시큐어 코딩 수칙이다. 화면에 쓰지도 않는 주민등록번호를 응답 패킷에 담아 보내는 것 역시 명백한 설계 결함으로 본다. 따라서 지금 대기업 통신사에서 동일한 취약점으로 수천만 건이 유출된다면, 보편적 보안 수준에 미치지 못했다는 이유로 의무 위반과 과징금 처분이 인정될 가능성이 크다.

## 5. 판결에 대한 의견과 실무에서 참고할 점

### 5.1 판결에 대한 의견

대법원이 원심의 좁은 해석을 깨고 **'DB와 연동되는 웹 서버도 개인정보처리시스템에 포함된다'**고 정리한 부분에는 동의한다. 실제 웹 서비스에서는 웹 서버와 DB가 함께 움직이며 개인정보를 처리하므로, DB만 보호 대상으로 한정하면 현실과 맞지 않는다. 해킹 결과만으로 처벌하는 결과책임을 경계한 기준 역시 타당하다.

다만 최종적으로 KT의 의무 위반을 인정하지 않은 결론은 다소 아쉽다. 판결문에도 나와 있듯, KT 웹 서버는 브라우저 화면에 띄우지도 않을 주민등록번호와 주소까지 응답 패킷에 실어 보냈다. 파라미터 변조 취약점을 사전에 모두 걸러내기 어려웠다는 점은 이해하더라도, 불필요한 민감정보까지 응답에 포함해 전송한 설계 문제까지 '합리적인 보호조치' 범위 안에서 용인해 준 것은 피해 규모에 비해 관대한 판단이었다고 생각한다.

### 5.2 실무에서 참고할 점

이 판례를 정리하며 서비스 개발과 보안 실무에서 챙겨야 할 세 가지를 정리해 보았다.

1. **인증과 인가를 분리해 검증하기**: 사용자가 정상 로그인했는지 확인하는 것(인증)에서 멈추면 안 된다. 데이터를 조회하거나 수정하는 모든 API 요청마다 요청된 식별자(계약번호, 주문번호 등)가 현재 로그인한 사용자의 소유가 맞는지 서버에서 반드시 확인(인가)해야 한다.
2. **응답 데이터 최소화하기**: 화면에 보여줄 정보만 골라서 응답 데이터에 담아야 한다. DB 조회 결과를 그대로 응답 패킷에 싣고 화면에서만 숨기는 방식은 프록시 도구나 브라우저 개발자 도구로 쉽게 노출될 수 있다.
3. **보안 점검 이력을 꾸준히 남기기**: 법원은 사고가 났을 때 기업이 평소 보안 적정성을 얼마나 검증하고 개선했는지를 중요하게 본다. KT가 승소할 수 있었던 결정적 근거도 자동화 점검 도구 연동, 정기 모의해킹, IPS 운영 기록이었다. 취약점 진단과 모의해킹, 조치 완료 내역을 체계적으로 기록해 두는 것이 기술적 방어이자 법적 리스크에 대비하는 가장 현실적인 방법이다.
