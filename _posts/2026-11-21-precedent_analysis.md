기업이 해킹을 당해 수천만 건의 고객 개인정보가 유출되었다면, 그 기업은 무조건 법적 처벌이나 과징금을 물어야 할까? 보안 사고가 터졌을 때 "기업이 할 만큼 했다"는 법적 기준을 어디까지로 보아야 하는지 명확히 짚어준 대표적인 판례가 있다. 바로 **대법원 2021. 8. 19. 선고 2018두56404 판결(KT 과징금 부과처분 취소 사건)**이다.

이 글에서는 판결문 원문을 바탕으로 해킹이 일어난 기술적 원리와 사건 경과, 2심 법원(원심)과 대법원의 법리 해석 차이, 그리고 현행 개인정보보호법 기준으로 본다면 결론이 어떻게 달라질지 알기 쉽게 정리한다.

## 2. 사건 경과 및 유출된 개인정보

이 사건은 웹 보안 분야에서 대표적인 취약점인 **파라미터 변조(Parameter Tampering)**, 더 구체적으로는 **IDOR(Insecure Direct Object Reference, 부적절한 직접 객체 참조)** 취약점이 악용된 사례다. 쉽게 말해, 서버가 "로그인한 사람이 맞는지"만 확인하고 "그 사람이 요청한 데이터가 정말 본인 것이 맞는지"는 확인하지 않아 발생한 사고다.

### ① 정상적인 요금 조회 흐름
1. 이용자가 KT 홈페이지에 아이디와 비밀번호를 입력하면, 웹 서버가 **통합인증 서버**를 통해 본인 여부를 확인한 뒤 인증 정보를 이용자 PC에 전달한다.
2. 회원으로 로그인에 성공하면, 9자리 숫자로 구성된 이용자 고유의 **서비스계약번호**가 브라우저의 **쿠키(Cookie, 로그인 상태 등을 임시 저장하는 작은 파일)**에 저장된다.
3. 이용자가 '요금명세서 보기'를 클릭하면 웹 브라우저가 이 서비스계약번호를 담아 웹 서버로 **요청 메시지(Request)**를 보낸다.
4. 웹 서버는 **데이터베이스(DB) 서버**에서 해당 번호의 요금 정보를 조회해 이용자 PC로 돌려주고(Response), 브라우저 화면에 표시한다.

### ② 해커의 공격 과정 (파라미터 변조)
1. 해커는 자신의 PC에 **파로스(Paros)**라는 웹 프록시(Proxy) 프로그램을 설치했다. 프록시 프로그램은 브라우저와 서버 사이에서 오가는 통신 데이터(패킷)를 중간에 가로채 내용을 들여다보거나 수정할 수 있는 도구다.
2. 해커는 본인 계정으로 정상 로그인한 뒤 '요금명세서 보기'를 눌렀다. 이때 요청 메시지가 웹 서버로 넘어가기 직전 파로스 프로그램으로 전송을 멈추게 했다.
3. 해커는 요청 메시지에 담긴 자신의 '서비스계약번호(파라미터)'를 **임의의 9자리 숫자**로 바꿔치기한 뒤 전송 버튼을 눌렀다.
4. KT 웹 서버는 요청에 담긴 서비스계약번호가 현재 로그인한 해커 본인의 번호인지 대조하지 않은 채, DB 서버에서 그 임의의 번호에 해당하는 다른 고객의 요금명세서 데이터를 그대로 가져와 응답으로 내려보냈다.

### ③ 유출 규모 및 문제가 된 개인정보
* **유출 기간:** 2013. 8. 8. ~ 2014. 2. 25. (약 6개월 이상 반복 수행)
* **유출 규모:** 총 **11,708,875건**
* **유출된 개인정보 항목:** 요금정보, **고객의 이름, 주민등록번호, 주소, 서비스가입정보** 등
* **주목할 기술적 문제점:** 이름, 주민등록번호, 주소 등은 실제 웹 브라우저 화면에는 보이지 않는 데이터였다. 하지만 웹 서버가 화면 표시에 필요하지 않은 민감정보까지 응답 패킷에 통째로 실어 보냈고(**과도한 데이터 노출, Excessive Data Exposure**), 해커가 파로스 프로그램으로 응답 패킷 원문을 뜯어보며 이 정보까지 모두 수집했다.

## 3. 양측 주장과 법원의 판단

### ① 판단에 쓰인 핵심 법 조항
당시 정보통신서비스 제공자(통신사, 포털 등)는 개인정보보호법이 아닌 **구 정보통신망법**의 적용을 받았다.
* **구 정보통신망 이용촉진 및 정보보호 등에 관한 법률 제28조 제1항 제2호:** 개인정보의 분실·도난·누출·변조 또는 훼손을 방지하기 위해 불법적인 접근을 차단하는 침입차단시스템 등 접근통제장치의 설치·운영 의무를 규정한다.
* **구 정보통신망법 시행령 제15조 제2항·제6항:** 개인정보를 처리할 수 있도록 체계적으로 구성한 데이터베이스시스템을 **'개인정보처리시스템'**으로 정의하고, 구체적인 보호조치 기준을 방송통신위원회 고시에 위임한다.
* **구 「개인정보의 기술적·관리적 보호조치 기준」(방송통신위원회 고시) 제4조 제9항:** 취급 중인 개인정보가 인터넷 홈페이지, P2P, 공유설정 등을 통해 열람 권한이 없는 자에게 공개되거나 외부로 유출되지 않도록 개인정보처리시스템 및 개인정보취급자의 컴퓨터에 조치를 취해야 한다고 규정한다.

### ② 양측의 주장 비교

| 구분 | 핵심 주장 |
| :--- | :--- |
| **피고 (개인정보보호위원회 / 구 방통위)** | KT가 파라미터 변조 같은 잘 알려진 웹 취약점을 방치해 1,170만 건이 넘는 대규모 개인정보 유출을 초래했다. 이는 고시 제4조 제9항의 기술적 보호조치 의무를 위반한 것이므로 과징금 부과 처분은 정당하다. |
| **원고 (KT)** | 사고 이전부터 국제웹보안표준기구(OWASP)가 발표한 10대 보안 취약점을 검출하는 자동화 점검 도구를 도입해 개발·유지보수 단계에 연동했고, 모의해킹(2012년 11월, 2013년 7월)과 국정원 인증 침입방지시스템(IPS) 운영 등 당시 보안 기술 수준에서 요구되는 조치를 다했다. |

### ③ 대법원의 판단 및 판결문 원문 인용

대법원은 이 사건을 두 가지 쟁점으로 나누어 판단했다. 결론적으로 **법리 해석(전제)은 피고(개보위)의 손을 들어주었으나, 실제 의무 위반 여부(결론)는 원고(KT)의 손을 들어주며 상고를 기각**했다.

#### 쟁점 1: 웹 서버도 '개인정보처리시스템'에 해당하는가? → 해당한다 (적극)
대법원은 고시 제4조 제9항이 기업 내부의 실수뿐 아니라 외부 해킹으로 인한 유출 방지도 직접 규율하며, DB와 연동된 웹 서버 역시 개인정보처리시스템의 일부라고 못 박았다.
> "이 사건 고시 제4조 제9항의 '개인정보처리시스템'은 개인정보의 생성, 기록, 저장, 검색, 이용과정 등 **데이터베이스시스템(DBS) 전체**를 의미하는 것으로, **데이터베이스(DB)와 연동되어 개인정보의 처리 과정에 관여하는 웹 서버 등을 포함한다**고 봄이 타당하다."

#### 쟁점 2: KT가 기술적 보호조치 의무를 위반했는가? → 위반하지 않았다 (소극)
대법원은 기업이 져야 할 보호조치 의무의 수준을 '완벽한 해킹 방지'가 아니라 **'사회통념상 합리적으로 기대 가능한 정도'**로 규정했다.
> "이 사건 고시 제4조 제9항에서 정보통신서비스 제공자 등의 의무로 규정하고 있는 조치는 '정보통신서비스 제공자 등이 취급 중인 개인정보가 인터넷 홈페이지 등에 대한 해킹 등 침해사고에 의해 유출되지 않도록 개인정보처리시스템과 개인정보취급자의 컴퓨터에 취하여야 할 **사회통념상 합리적으로 기대 가능한 정도의 기술적 보호조치**'라고 해석할 수 있다."

대법원이 KT의 의무 위반을 인정하지 않은 구체적 이유는 다음과 같다.
1. **대규모 소프트웨어의 한계:** 방대한 소스코드와 수많은 파라미터 입력 경우의 수가 존재하는 시스템에서, 개발 단계부터 모든 파라미터 변조 예외 상황을 완벽히 예상해 차단하기는 어렵다.
2. **당시 개발 관행:** 정상 로그인을 마친 이용자라면 권한이 보장된다고 전제하고 프로그램을 설계하는 것이 당시로서는 통상적이었으며, 보편적인 정보보안 기술 수준에 미치지 못했다고 보기 어렵다.
3. **결과책임 경계:** 사고 이후 KT가 파라미터의 계약번호와 로그인 이용자 정보를 대조하도록 소스코드를 쉽게 수정했다고 해서, 그 사후 조치의 용이성만 보고 법 위반을 단정하는 것은 기업에 무리한 결과책임을 묻는 것이다.
> "사후 시정조치가 비교적 손쉽게 이루어졌다는 사정에만 주목하여 이 사건 고시 제4조 제9항 위반 여부를 판단한다면 이는 **결과책임을 묻는 것으로 귀결될 우려**가 크다."
4. **지속적인 사전 보안 노력:** KT는 2006년부터 **OWASP 10대 웹 취약점 자동화 점검 도구**를 자체 보안점검관리 포털에 연동해 개발·유지보수 단계에서 활용했고, 2012~2013년에 걸쳐 **모의해킹**을 수행했으며, 국가정보원 IT보안인증사무국 인증 **침입방지시스템(IPS)**을 설치·운영하는 등 취약점을 최소화하려는 노력을 충분히 기울였다.

## 4. 상급심 비교 및 현행법 기준 검토

### ① 원심(서울고등법원) vs 대법원 비교
이 판례는 **최종 결론(KT 승소)은 같지만, 대법원이 원심의 잘못된 법리 해석을 정면으로 바로잡은 사례**라는 점에서 의미가 크다.

| 비교 항목 | 원심 (서울고등법원 2016누64533) | 대법원 (2018두56404) |
| :--- | :--- | :--- |
| **고시 제4조 제9항의 적용 범위** | 기업 내부적 요인(실수 등)에 의한 유출 방지용이며, 파라미터 변조 같은 외부 해킹 방지는 직접 규율하지 않음 | 내부 부주의뿐 아니라 **외부 해킹 등 불법적 접근에 의한 유출 방지도 직접 규율함** (원심 판단 부적절 지적) |
| **웹 서버의 시스템 포함 여부** | 내부 영역의 데이터베이스관리시스템(DBMS)만 해당하며, 웹 서버나 웹 페이지는 포함되지 않음 | DB와 연동되어 개인정보 처리 과정에 관여하는 **웹 서버 등 데이터베이스시스템(DBS) 전체가 포함됨** |
| **KT의 보호조치 의무 위반 여부** | 위반 아님 (원고 승소) | **위반 아님 (상고 기각)** — 당시 보안 기술 수준에 맞는 합리적 보호조치 이행 인정 |

### ② 사건 이후 법 개정 내용과 현재 기준 결론 예측
이 사건은 2013~2014년에 발생한 사고에 대해 구 정보통신망법이 적용되었다. 이후 개인정보 관련 법령은 크게 두 차례 큰 변화를 겪었다.

1. **법령 통합 (2020년 데이터 3법 개정):** 구 정보통신망법에 있던 개인정보 보호 규정이 **「개인정보 보호법」**으로 일원화되었다. 이에 따라 기존 고시 제4조 제9항의 내용은 현재 **개인정보보호법 제29조(안전조치의무)**, **시행령 제30조**, 그리고 **「개인정보의 안전성 확보조치 기준」 제6조 제3항**으로 통합·계승되었다.
2. **제재 수위 대폭 강화 (2023년 전면 개정):** 개인정보 유출 시 과징금 상한이 기존 '위반행위 관련 매출액의 3%'에서 **'전체 매출액의 3%(위반행위와 관련 없는 매출액 제외)'**로 대폭 상향되었다.

그렇다면 **2026년 현재 기준으로 똑같은 사고가 발생해도 KT가 승소(면책)할 수 있을까?**
* **법리적 측면:** 대법원이 세운 "사회통념상 합리적으로 기대 가능한 수준의 보호조치" 및 "해킹 발생 자체만으로 처벌하는 결과책임 불가" 원칙은 현행법 아래에서도 그대로 유지된다.
* **실무·기술적 측면 (결론이 달라질 가능성 높음):** 대법원은 보호조치 이행 여부를 판단할 때 **'사고 당시 보편적으로 알려진 정보보안 기술 수준'**을 핵심 기준으로 본다. 2013년과 달리 오늘날에는 파라미터 변조(IDOR) 방어를 위한 **서버 측 세션-객체 권한 검증**이 웹 개발의 가장 기초적인 시큐어 코딩(Secure Coding) 수칙으로 자리 잡았다. 또한 화면에 쓰지 않는 주민등록번호를 API 응답에 그대로 노출하는 설계 역시 명백한 보안 결함으로 취급된다. 따라서 현재 대기업 통신사에서 동일한 취약점으로 수천만 건이 유출된다면, **보편적 보안 수준 미달로 보호조치 의무 위반이 인정되어 막대한 과징금이 부과될 가능성이 매우 높다.**

## 6. 판결에 대한 의견 및 실무 시사점

### ① 판결에 대한 본인 의견
대법원이 원심의 좁은 해석을 깨고 **'DB와 연동되는 웹 서버도 개인정보처리시스템에 포함된다'**고 명확히 선언한 점에는 전적으로 동의한다. 현대의 웹 서비스는 웹 서버(WAS)와 DB가 긴밀하게 결합해 개인정보를 처리하므로, DB만 보호 대상이라고 본다면 현실의 보안 공백을 방치하는 꼴이 되기 때문이다. 또한 해킹이 일어났다는 결과만 보고 기업에 무조건 책임을 묻는 '결과책임'을 경계한 점도 합리적이다.

다만, **최종적으로 KT의 보호조치 의무 위반을 부정하고 면책해 준 결론에는 다소 아쉬움이 남는다.** 판결문에도 명시되어 있듯, KT 웹 서버는 웹 브라우저 화면에 표시하지도 않을 **주민등록번호와 주소**까지 응답 패킷에 실어 보냈다. 파라미터 변조 취약점을 사전에 모두 찾아내기 어려웠다는 점은 일부 참작하더라도, 불필요한 민감정보를 응답 데이터에 포함해 전송한 설계 결함까지 '당시 기술 수준에서 합리적인 조치'로 용인해 준 것은 이용자 피해 규모(약 1,170만 건)에 비해 기업에 다소 관대한 기준이 적용된 측면이 있다고 본다.

### ② 개발·보안 실무에서 참고할 점
이 판례는 서비스 개발자와 보안 담당자에게 세 가지 명확한 실무 교훈을 준다.

1. **인증(Authentication)과 인가(Authorization)의 철저한 분리:**
   이용자가 정상적으로 로그인했는지 확인하는 것(인증)만으로는 부족하다. 특정 데이터(요금명세서, 주문내역 등)를 조회·수정하는 모든 API 요청마다 **"요청된 객체 ID(서비스계약번호 등)가 현재 로그인된 세션 주인의 소유가 맞는지"** 서버 측에서 반드시 검증(인가)해야 IDOR·파라미터 변조 공격을 막을 수 있다.
2. **데이터 최소화 원칙(Data Minimization) 준수:**
   프론트엔드 화면에 보여줄 데이터만 선별해 DTO(Data Transfer Object)로 내려보내야 한다. DB 테이블의 컬럼 전체를 응답 패킷에 실어 보내고 화면에서만 숨기는 방식은 프록시 툴이나 브라우저 개발자 도구로 손쉽게 탈취당할 수 있는 치명적 취약점이다.
3. **보안 활동의 지속성과 증적(Evidence) 관리:**
   법원은 사고 발생 시 기업의 책임 여부를 가릴 때 **'평소에 얼마나 지속적으로 보안 적정성을 검증하고 개선했는가'**를 핵심 판단 근거로 삼는다. 실제 KT가 승소할 수 있었던 결정적 이유도 소스코드 보안 점검 도구 연동, 정기 모의해킹, IPS 운영 기록이 남아 있었기 때문이다. 실무에서는 시큐어 코딩 점검, 취약점 진단, 모의해킹 및 조치 완료 이력을 체계적으로 문서화해 관리하는 것이 기술적 방어이자 가장 강력한 법적 리스크 대응 수단이 된다.
